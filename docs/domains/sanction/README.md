# Sanction

회원 제재 도메인이다(이슈 #569). 관리자가 신고된 댓글을 숨기면 작성자에게 경고가 쌓이고, 경고 횟수에 따라 기간제로 **댓글 작성·수정이 제한**된다. 관리자가 직접 제한을 걸거나 해제할 수도 있다. 외부 API 계약은 [Sanction API](api.md)를 따른다.

## 책임

- 소유: `member_sanction` 테이블(`V70`). 제재 생성·해제와 "지금 이 회원이 제한 중인가" 판정.
- 소유하지 않음: 댓글 숨김 판단(Post), 알림(Notification), 회원 존재·역할(Member). 다른 도메인의 Entity·Repository로 상태를 바꾸지 않는다. Post는 `SanctionService`·`SanctionQueryService`를 통해서만 호출한다. 예외로 대상 회원 행을 잠글 때만 `MemberRepository.findByIdForUpdate`를 쓴다(관심 분야 저장·댓글 신고 접수와 같은 방식).

## 정책

| 항목 | 값 | 설정 |
| --- | --- | --- |
| 경고 대상 | 관리자가 **숨긴** 댓글의 작성자(게시글 작성 Creator 본인 포함) | - |
| 경고 집계 기간 | 최근 90일 | `cking.sanction.warning-window` (기본 `P90D`) |
| 단계별 제한 | 경고 1회 1일, 2회 3일, 3회 이상 7일 | `cking.sanction.comment-restriction-steps` (기본 `P1D,P3D,P7D`, 마지막 값이 그 이상 횟수에 계속 쓰인다) |
| 제한 범위 | 댓글 작성·수정. 삭제는 막지 않는다 | - |
| 자동 제재 | 신고 건수만으로는 하지 않는다. 관리자가 숨긴 댓글만 경고가 된다(집단 신고로 남을 제재하는 것을 막는다) | - |

- **기록은 삭제하지 않는다.** 90일은 경고를 세는 기준일 뿐이며, 오래된 경고는 집계에서만 빠진다. 보관 기간과 삭제 정책은 정하지 않았다(법적 보관·파기 요건이 생기면 별도로 정한다).
- 경고가 쌓일 때마다 그 횟수에 맞는 제한을 **따로 새로 만든다.** 제한이 겹쳐도 합치지 않고, 작성 가드는 유효한 제한 중 **종료 시각이 가장 늦은 쪽**을 쓴다.
- 자동 경고는 해제해도 **경고 횟수에는 남는다**(제한만 풀린다). 수동 제한은 경고 횟수에 세지 않는다.
- 제한이 시작될 때(자동 경고, 수동 제한)와 **유효한 제한이 모두 풀렸을 때**(해제) 작성자에게 알림을 보낸다. 다른 제한이 남아 있으면 해제 알림을 보내지 않고, 이미 끝났거나 해제된 제한을 다시 해제해도 알리지 않는다. 같은 제재의 같은 종류 알림은 한 번만 생긴다. 제한 시작 알림이 안내하는 해제 시각은 방금 만든 제재 하나가 아니라 **지금 유효한 제한 중 가장 늦게 끝나는 시각**이다(작성 가드가 적용하는 시각과 같다). 30일 수동 제한이 있는 회원에게 1일 경고가 붙어도 알림은 30일 뒤를 안내한다. 수동 제한의 사유는 알림에 담지 않는다. 해제 알림은 해당 제한이 풀렸다는 사실만 알리고 "다시 댓글을 작성할 수 있다"고 약속하지 않는다. 플랫폼 제한과 스페이스 차단이 따로 남아 있을 수 있기 때문이다.
- 이의 신청과 신고 남용 제한은 범위 밖이다(신고 남용은 신고자별 1시간 20건 한도가 있다).

## 데이터

| 컬럼 | 의미 |
| --- | --- |
| `member_id` | 제재 대상 |
| `scope` / `type` | `PLATFORM`(관리자·댓글 숨김 경고) 또는 `SPACE`(크리에이터가 자기 스페이스에서 건 차단, 이슈 #579) / `COMMENT_RESTRICTION` |
| `space_creator_id` | `scope=SPACE`일 때 차단을 건 스페이스의 주인(Creator). `PLATFORM`은 NULL이며 `ck_member_sanction_space_creator`가 둘의 짝을 강제한다(`V72`). 이때 `created_by`는 차단을 건 크리에이터의 member_id다 |
| `source` | `AUTOMATIC`(관리자의 댓글 숨김, 경고 집계 대상) / `MANUAL`(관리자 수동, 집계 제외) |
| `cause_comment_id` | 자동 경고의 원인 댓글. **UNIQUE**라 같은 댓글로 경고가 두 번 쌓이지 않는다. 댓글이 삭제돼도 기록이 남도록 FK는 두지 않는다 |
| `started_at` / `ends_at` | 제한은 `started_at <= now < ends_at` 동안 유효하다 |
| `released_at` / `released_by` | 관리자 해제. 해제 시각부터 무효다 |

인덱스: `(member_id, source, started_at)`은 경고 집계, `(member_id, ends_at)`은 댓글 작성마다 하는 유효 제한 조회, `(started_at, sanction_id)`는 관리자 목록 정렬이다.

## 크리에이터의 스페이스 댓글 차단 (이슈 #579)

크리에이터가 자기 스페이스의 게시글에서만 특정 회원의 댓글 작성·수정을 막는다. 같은 `member_sanction` 테이블의 `scope=SPACE` 행이다.

| 항목 | 값 |
| --- | --- |
| 거는 사람 | 그 스페이스의 Creator 본인, 또는 관리자(크리에이터를 지정해 어느 스페이스에서든, 이슈 #584). 관리자는 크리에이터가 건 차단도 풀 수 있고, 크리에이터는 관리자 API를 쓸 수 없다. `created_by`가 건 사람이다 |
| 기간 | 1~365일. 영구 차단은 없다 |
| 범위 | 그 크리에이터의 게시글 댓글 작성·수정만 막는다. 다른 스페이스, 삭제, 좋아요·팔로우는 막지 않는다 |
| 경고·단계 | 경고 횟수에 세지 않고(`source=MANUAL`) 플랫폼 제재 단계에도 영향을 주지 않는다 |
| 중복 | 같은 크리에이터가 같은 회원에게 이미 유효한 차단이 있으면 새로 만들지 않고 기존 차단을 돌려준다. 기간을 바꾸려면 해제 후 다시 건다 |
| 차단 대상 제한 | 거는 사람 본인은 차단할 수 없다(`CANNOT_BLOCK_SELF`). 관리자도 차단할 수 없다(`CANNOT_BLOCK_ADMIN`). 스페이스 주인은 자기 스페이스에서 차단할 수 없다(`CANNOT_BLOCK_SPACE_OWNER`, 관리자가 지정한 경우 포함). 역할은 대상 회원 행을 잠근 뒤 확인한다 |
| 알림 | 시작·해제 때 차단된 회원에게 알림(종류는 플랫폼 제한과 같은 `COMMENT_RESTRICTION_STARTED`·`RELEASED`, 본문에 크리에이터 이름). 사유는 없다 |
| 플랫폼 제재 API와의 관계 | `GET /api/admin/sanctions`는 `PLATFORM`만 보여주고, `POST /api/admin/sanctions/{id}/release`로 스페이스 차단을 풀려 하면 `RESOURCE_NOT_FOUND`다. 스페이스 차단의 관리자 API는 `/api/admin/comment-blocks`다 |

댓글 작성·수정 가드(`requireCommentWriteAllowed(memberId, creatorId)`)는 플랫폼 제한을 먼저, 그 스페이스의 차단을 다음에 확인한다. 둘 다 있으면 플랫폼 제한(`COMMENT_RESTRICTED`)을 먼저 알린다.

잠금: 차단은 대상 회원과 차단을 거는 크리에이터의 회원 행을 **회원 ID 오름차순으로 둘 다** 쓰기 잠금으로 먼저 읽는다. 제재 INSERT·해제 UPDATE의 `created_by`·`released_by` FK 검사가 크리에이터 회원 행의 공유 잠금을 요구하는데(READ_COMMITTED에서도 유지), 대상 행만 잠그면 크리에이터 A가 B를, B가 A를 동시에 차단할 때 서로 상대 행을 기다리는 교착이 생기기 때문이다. 같은 순서로 두 행을 잠그면 한쪽이 끝날 때까지 기다린다. **관리자**가 차단·해제할 때는 대상 회원 행만 잠근다. 관리자는 스페이스 차단의 대상이 될 수 없어 다른 차단이 관리자 행을 쓰기 잠금으로 잡지 않고, 플랫폼 제재 경로도 대상 행을 먼저 잠근 뒤 `created_by`·`released_by` FK로 관리자 행의 공유 잠금만 요구한다. 관리자 행을 먼저 쓰기 잠금으로 잡으면 같은 관리자가 같은 대상에게 보낸 플랫폼 제한과 서로 기다리는 교착이 생기므로 잠금 순서(대상 → 관리자 FK)를 플랫폼 제재와 맞춘다. 같은 회원에 대한 중복 차단과 댓글 작성(역시 회원 행을 먼저 잠근다)도 이 잠금으로 직렬화된다. 해제는 제재 행 → 회원 행(오름차순) 순서이며 변경 메서드는 `READ_COMMITTED`로 실행한다.

## 흐름

1. 관리자가 `POST /api/admin/comment-reports/{commentId}/hide`로 댓글을 숨긴다(Post).
2. 같은 Transaction에서 작성자 행을 잠그고 `SanctionService.recordCommentHide`가 집계 기간 안의 자동 경고 수를 센 뒤 경고 겸 제한을 저장한다. 이미 숨긴 댓글을 다시 숨기면 경고를 새로 쌓지 않는다.
3. 같은 Transaction에서 작성자에게 제한 시작 알림이 저장된다([Notification](../notification/README.md), 이슈 #572). 경고 횟수와 해제 시각(UTC)이 본문에 들어간다.
4. 작성자가 댓글을 쓰거나 고치면 `SanctionQueryService.requireCommentWriteAllowed`가 유효한 제한을 확인하고, 있으면 `COMMENT_RESTRICTED`(403)이며 메시지에 해제 시각(UTC)을 담는다.

## 동시성

경고 횟수를 읽고 새 경고를 저장하는 두 단계이므로 같은 작성자의 서로 다른 댓글이 동시에 숨겨지면 둘 다 같은 횟수를 읽을 수 있다. 숨김 처리는 **작성자 행 → 게시글 공유 잠금 → 댓글 쓰기 잠금** 순서로 잠가 같은 작성자의 처리를 직렬화한다. 댓글 신고 접수의 잠금 순서(신고자 → 게시글 → 댓글)와 같아 교착이 생기지 않는다. 수동 제한은 대상 회원 행만 잠그고, 경고와 수동 제한 모두 알림에 담을 가장 늦은 종료 시각을 동시에 커밋된 제한까지 보도록 `READ_COMMITTED`로 실행한다. 해제는 제재 행 → 회원 행 순서로 잠그고 `READ_COMMITTED`로 실행해, 겹친 두 제한을 동시에 해제할 때 서로 상대가 아직 유효하다고 읽어 해제 알림이 빠지는 일을 막는다. 제재 행을 잠그는 흐름은 해제뿐이라 교착이 생기지 않는다.

**숨김은 `READ_COMMITTED`로 실행한다.** 관리자 검증과 작성자 조회가 작성자 행 잠금보다 먼저 있어, REPEATABLE READ에서는 그 일반 조회가 스냅샷을 고정한다. 잠금에서 기다렸다가 풀려도 경고 집계가 앞선 요청이 커밋한 경고를 못 보고, 같은 작성자의 서로 다른 댓글을 동시에 숨기면 두 제한이 모두 1일로 저장된다(3일이어야 한다). READ_COMMITTED는 문장마다 최신 커밋을 읽으므로 잠금 이후의 집계가 앞선 경고를 센다.

**댓글 작성·수정도 같은 회원 행 잠금을 먼저 잡는다.** 잠금 없이 회원을 일반 조회한 뒤 제한을 확인하면, MySQL 기본 REPEATABLE READ가 첫 일반 조회 시점의 스냅샷을 고정해 그 사이 관리자가 확정한 제재를 못 보고 댓글이 저장될 수 있다. 회원 행을 쓰기 잠금으로 먼저 읽으면(트랜잭션의 첫 DB 접근) 진행 중인 제재 처리가 끝날 때까지 기다리고, 잠금 이후 첫 일반 조회에서 만들어지는 스냅샷으로 제한을 읽는다. 잠금 순서는 작성자 → 게시글 → 댓글로 숨김 처리·신고 접수와 같고, 삭제는 제한을 확인하지 않으므로 회원 행을 잠그지 않는다. 같은 회원의 댓글 작성·수정은 서로 직렬화된다.
